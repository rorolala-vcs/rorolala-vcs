# 如何写技术文档：先判断，再落笔

动笔前先判断：读者处在什么位置，这一句在为他做什么，删掉之后他会缺什么。格式是判断的结果；先有判断，再选格式。

## 动笔前先回答三个问题

1. **读者是谁，已经会什么。** 默认读者是有经验的开发者，会装环境、会用常见工具。他需要这个项目的事实、约束和路径；编程入门知识已具备。判断内容去留时，用这个尺子：删掉之后，他还能不能完成操作。
2. **他读到这里要做什么。** 文档通常服务于一个动作：定位、执行、排错、查参数。同一段出现两个动作，读者需要切换注意力。先确定这一段支持哪个动作，再决定写什么。
3. **这句话删掉，他会缺什么。** 缺一个条件、一个结果、一个风险，就保留；什么都不缺，就删。重复前提、空泛过渡、常识解释，通常属于后者。

## 语气

以专业、清晰、务实、友好的语气写作。像一份面向开发者和技术创作者的正式项目 README：自信说明产品价值，保持克制；内容以说明事实为主，降低使用门槛。

- **用第二人称和祈使句。** 直接称读者“你”，用“安装依赖”“运行下面的命令”这样的祈使句引导操作步骤。结构分明，善用标题、列表、代码块和加粗突出关键概念与流程。
- **指导性强，简洁直接。** 术语要准确；必要时解释设计理念，点到为止。
- **表达积极但客观。** 对项目能力有自信，不承诺做不到的事。
- **用说明承担信息。** 形容词只在不影响判断时保留；删掉冗长抒情、营销式夸张和情绪化表达。

## 写作姿态

- **陈述事实、条件和结果，让读者自己判断。** 不评价读者的水平或选择，不用“显然”“非常简单”替他下结论。有约束就写出约束和原因；没有约束，就不用“必须”“不能”制造紧张。
- **直接陈述。** 先否定再肯定的句式要求读者先否掉一个错解才拿到正解；“A 是什么，B 是什么，由……分两步落地”“不是……而是……”“不，只是……”都属于这类句式。“……是什么”式的定义罗列和“由……等一系列”式的铺垫同样属于此类。直接写你要说的那件事。
- **对读者诚实。** 不确定的地方标明范围：“当前版本”“在这个平台上”。做不到、会失败、有代价，直接写出来。需要读者另查的内容，给链接或指路，不在这里复述。
- **保留作者判断，控制情绪表达。** 作者的存在感来自判断和语气。少量“一般来讲”“当然”“这里有个坑”可以让文字有温度；感叹号、反问、夸张形容词会让读者记住态度而不是信息。正式内容（贡献指南、许可证说明）用规范、正式的写法，不加个人口吻。
- **密度来自删掉不承载信息的句子。** 信息密度靠每句承担一点新东西；把句子压短不增加密度。删掉不承载信息的句子，密度自然上来；为了压缩而省掉条件、对象或结果，读者反而要回头猜。宁可多一句把前提说清，也不用一句漂亮话换来歧义。

## 把结构想清楚

- **一段只推进一件事。** 段落的边界由意图决定，长短不作为依据。读者读完一段，应该能说出“这段告诉我什么”。如果一段同时在定位、操作和解释，就拆开；如果几句话都在说同一件事，就合并。段落之间留空行，让意图的边界可见；空行不承担版面装饰。
- **动作和原因分开。** 执行步骤和机制解释分开写。先给动作，再解释原因；或者先交代原因，再给动作。两种顺序都可以，交错不行。警告单独成段或放进提示框，不要夹在步骤中间。
- **示例放在读者动手的位置。** 用他可以照抄的命令和可观察的输出。示例按最可能的使用顺序排列：默认用法在前，显式参数和边缘情况在后。示例能说明的，不在正文复述；示例结束后就结束，不补总结、对照表或“综上所述”。没有示例时，结尾也只收束，不引入新信息。
- **形式跟着关系走。** 排版把关系变得可见；先确定关系，再选列表、表格或图。

  | 内容之间的关系     | 通常的形式         |
  | ------------------ | ------------------ |
  | 并列、步骤、检查项 | 列表；有先后就编号 |
  | 查找、对照         | 表格               |
  | 顺序、依赖、层级   | 图或编号           |
  | 需要照抄的内容     | 代码块             |

  表格适合回答“某个值是什么”，不适合承载推理；单元格写到“是什么”为止，不放教程。平台差异要落到具体值；多系统对照时，表格通常比一句话清楚。图的节点名与正文一致；关系能用一句话说清时就省掉图。

- **标题是承诺。** 标题说多少，正文就写多少。用平实的说明性名词，避免“介绍”“浅谈”这类无法判断范围的说法。

## 句子和用词

- **一句话只推进一件事。** 主语和动作要明确，条件、动作、结果按发生顺序写。定语套得太长、读起来要回头的句子，拆开。连接词该用就用：因为、所以、但、如果、先、再、最后；它们让关系显形，不算赘余。
- **用可观察的事实说话。** 优先写读者能验证的东西：命令、路径、退出码、输出、版本号。概括词只在无损于判断时才用。“失败”写成“非零退出码”；“配置一下”改写为要改的键和值。读者能照着做的描述，比听起来顺的描述有用。
- **词要稳定，程度词要有依据。** 同一个对象用同一个名字，第一次出现时点明它是什么。程度词只在传达约束时保留：“任意”“必须”有信息量，“非常简单”“只需”通常没有。关键条件、约束或结论可以加粗，一段最多一处，标词不标整句。
- **人称可以自然。** 可以直接称读者“你”，也可以保持无人称的陈述。选一种读起来顺的方式，不必为了客观而刻意回避第二人称。

## 提醒的取舍

提醒用于管理风险。只有读者可能因此失败、丢数据、浪费大量时间，或者平台、版本、顺序、依赖存在差异时才给。

形式跟着风险走：

| 风险类型       | 形式       |
| -------------- | ---------- |
| 一句事实       | 正文       |
| 关键约束       | 加粗一个词 |
| 坑、捷径、特例 | 提示框     |

加粗和提示框不重复正文已经说过的话。

读者已经会的基础、显而易见的后果、正文已经解释清楚的事，不写提醒。直接说会发生什么。

写命令之前，先确认它在读者的目录、权限、shell 和平台上能跑。

## 写完之后，用问题检查

- 假设读者只读标题、代码块和表格，他能完成操作吗？
- 每一段删掉，读者会缺什么？如果答不上来，就删。
- 哪些句子只是在解释自己刚说过的话？
- 哪些句子用了“A 是什么，B 是什么，由……”式的定义罗列或“先否定再肯定”的句式？把它改成直接陈述。
- 哪些地方需要读者回头找前提？把前提移到前面。
- 示例结束后，读者还需要我再说一句吗？如果需要，补进示例；如果不需要，停笔。
- 提醒是否落在真正会失败的那一步？有没有重复正文？
- 标题承诺的范围，正文是否都兑现了？

## 常见失衡

| 表现                     | 背后的问题                 | 调整方向                       |
| ------------------------ | -------------------------- | ------------------------------ |
| 篇幅很长，读完仍不会操作 | 在解释系统，而不是支持动作 | 先写操作路径，再补必要的原因   |
| 每段都对，连起来不顺     | 段落在并列信息，没有推进   | 按读者的动作顺序重排           |
| 读起来像模板             | 句子在占位，不在回答       | 逐句问“删掉会缺什么”           |
| 提醒很多，读者仍出错     | 提醒没有落在风险点         | 把提醒移到会失败的那一步       |
| 格式很多，重点仍不突出   | 形式没有对应关系           | 先确定关系，再选列表、表格或图 |

## 一句话

先想清楚读者此刻要做什么，再决定每一句、每一段、每一种格式是否该存在。通顺地说事实，删掉不承载信息的话；提醒只在会出事的地方给，语气留在表面。
