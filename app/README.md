# Contributing

`app/` holds the programs a user runs: the command line, the daemon, the desktop program, the
launcher, the C ABI and the two native daemon windows. What each one is belongs in the README beside
it. This page says what a contribution here looks like and what the machine needs.

## What can be contributed

- A command under `app/cli/`. It is one file, one node and one shape, and
  `app/cli/rola/src/cmd_bring.rs` is the example to follow. The words it prints live in
  `app/cli/*/i18n/` and are stated in both languages.
- The C ABI under `app/ffi`, and any `#[lazyffi]` item in `src/`, `modules/` or `utils/`. The header
  is generated by the root `build.rs`, so no caller edits it by hand.
- The desktop program under `app/desktop`: the shell, the contract its plugins share, the four
  plugins that ship and the icons the window wears.
- The launcher under `app/launcher`.
- The two native daemon windows: `app/daemon-win` in Win32 C11 and `app/daemon-linux` in GTK 4 C11.
  Each carries its build script under `scripts/`.

## What it needs

- Rust 1.85 or newer. The workspace is edition 2024, and `git` is needed because `mingling` is taken
  from a git revision.
- On Windows, the MSVC build tools and the Windows SDK, which compile the resource script each
  program links its icon from.
- For the desktop program, the launcher and the C# binding, the .NET SDK that `global.json` pins,
  with `cargo` on `PATH`, because the binding is generated from the C header the Rust side writes.
- For `app/daemon-linux`, a C compiler, `pkg-config` and GTK 4.10 or newer.
- For `app/daemon-win`, Visual Studio Build Tools with the C++ x64 workload.

## Checks

`cargo ci fmt-check`, `cargo ci i18n`, `cargo ci clippy` and `cargo ci doc` cover the Rust side. The
C ABI is checked as C by `tests/ffi-c`, which `cargo ci integration-test` runs where a POSIX C
toolchain and a shared library both exist. The .NET side is `cargo ci dotnet-lint` and
`cargo ci dotnet-check`, and the desktop suites run in `cargo ci integration-test`.
